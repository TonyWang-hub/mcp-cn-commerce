# Pro 咨询回复手册

用途：为后续 `[Pro] 咨询` 提供事实一致的回复草稿；修改本文不表示已经发送回复。当前能力按 Core `6b6a7f9` / Pro `64dc3f5` 校准（2026-09-11），见 [SDK 能力表](sdk-integration.md#catalogue-and-evidence-status)与[候选验收状态](release-readiness.md)。

## 0. 原则

1. 项目提供商家授权范围内的只读数据连接，不承诺所有平台/数据域当前可用。
2. 注册工具、已核合同、SDK 可调用、真实店铺验证分开说明；所有平台尚未完成真店验收。
3. 优先围绕抖店、淘宝等已核订单/售后范围安排 1–2 平台 PoC。广告主信息和余额不能替代千川/巨量消耗、ROAS、计划报表；拼多多经营业务 schema 仍缺失，不能借多多进宝/万相台的名称称已接入。
4. Pro 已有多授权管理、相应 provider 的刷新、持久采集和报告；按平台、应用模式及店铺范围确认。没有现成的 Pro 巨量/千川自动续期承诺。
5. 继续履行 README 的“免费使用 Pro 内测版，换取真实场景反馈”招募承诺；本地试用机制不自动替代已给种子用户的安排。正式 OEM/SaaS/再分发等权利另由合作条款约定。

## 1. 一次收集试点输入

先收集非秘密信息；相关材料统一汇总，不分轮索要密钥：

| 输入 | 需要确认的内容 |
| --- | --- |
| 平台与数据域 | 首选 1–2 平台；订单/退款、商品/库存、广告、账单分别列，不能只问平台名称 |
| 应用与资格 | 自用/ISV/工具型等实际应用类型、获批 API 权限包；平台许可不能用 Pro 本地 scope 代替 |
| 店铺和身份 | 店铺数量、同/跨渠道、授权主体字段、是否有多个应用 key；不让客户在 issue 粘贴 token |
| 已有样本 | 至少两页可读数据、父子订单、支付优惠、部分退/失败/跨日样本及后台对照 |
| 部署和授权入口 | 本地单商家或合作方服务、受信身份、已登记 callback/IP 白名单；HTTPS 回调需要服务端接入 |
| 生命周期与验收 | 刷新/撤销/重新授权的可用测试窗口、希望核对的报表口径及未验证项 |

应用 secret、商家 token、授权 code 和买家资料保留在受控部署侧。账号资格、官方 schema、合作方适配与真实样本分别记录，不把全部缺口概括为“只差 token”。

## 2. 回复模板 A — 简短版

> 当前可以围绕已核订单和售后范围安排免费内测，优先用抖店、淘宝中的 1–2 个获准店铺做只读调用与后台核对。Pro 已有多授权管理、持久采集和报告，但具体平台能力以当前操作目录和授权合同为准，尚未完成真店验收。
>
> 巨量/千川广告报表与授权账户树、拼多多经营接口合同仍需补齐。先集中确认所需数据域、应用资格、可读样本和部署方式，再确认本次 PoC 的通过标准。密钥和商家 token 留在你的受控部署侧，无需发到 issue。

## 3. 回复模板 B — 技术边界版

> Core 提供显式凭证的只读 SDK 和各平台 MCP 入口；Pro 复用 Core，增加相应平台的授权与刷新、租户/店铺访问控制、采集和报告。已登记且获平台允许的 loopback 可使用 CLI，合作方 HTTPS 回调和用户身份需要服务端接入。
>
> 当前优先验证抖店、淘宝已核的订单和售后读范围；京东已增加售后专项查询，但没有完整退款采集。小红书 Source 时间字段、拼多多业务 schema、快手授权主体和微信共享组件跨 tenant 等边界仍需补齐。商品、库存、物流、评价、营销、广告和账单不按平台工具数量整体承诺。
>
> 我们可以按现有免费内测安排先核对 1–2 平台的实际样本、分页、金额日期和授权生命周期，再依据结果讨论正式交付。已通过工程测试与真实店铺通过会分别记录。

## 4. 演示与验收衔接

无需平台授权的演示只使用 `templates/` 中的模拟数据，并在输出写明“模拟数据，不证明真实平台可用”。广告/评价/库存等分析模板不能当作对应 API 已接通的展示。

真实 PoC 使用商家已有且获准的只读样本。逐项记录授权主体、方法、窗口/分页、实际金额/日期、后台核对、刷新/撤销/重新授权；不能为凑样本擅自下单、退款或改店铺配置。缺少两页或跨日样本时将相应项写成“未执行”，不拿模拟响应补签。

完成后回复限定在实际验证的应用、店铺、操作和样本，报告是已观测记录的汇总；不能把观察净额称银行到账、利润或完整资金结算。
