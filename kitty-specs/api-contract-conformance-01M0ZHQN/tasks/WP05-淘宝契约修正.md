## ⚠️ 签名参与集合：现状是坏的（本 WP 必须修）

`shared/cn_commerce_base.py:2900` 先算 `sign`、`:2901` 才把 `sign_method` 加进发送参数，而 `_sign`（`:3010`）又显式把 `sign_method` 排除。结果是 **`sign_method` 发了但没参与签名**。

TOP 官方规则是「除 `sign` 和 byte[] 外的全部参数入签」，所以这是真实的验签失败源，也违反本 WP 通用约束 #1 的不变式。

**修法二选一**（在契约声明里记录选了哪个及理由）：
- 让 `sign_method` 参与签名（符合官方规则，推荐）
- 或干脆不发 `sign_method`（TOP 默认 md5；但我们若用其他摘要就必须发）

注意这条**不是淘宝独有** —— `sign_method` 发而不签是 base class 的通病，WP02 的策略层应从机制上消除它（签名集合恒等于发送集合减 `sign`），各平台再按自己的规则声明该参数是否发送。

## 签名摘要与拼接（现状已符合官方，保持）

`md5`：`UPPER(MD5(secret + Σ(key+value, ASCII码位升序) + secret))`，除去 `sign` 和 byte[] 参数，无分隔符，UTF-8。base class 现有实现逐条符合，包括「key 或 value 为空则整个参数跳过」（官方 SDK 强制，文档未写）。

官方算例（WP01 已固化为硬断言）：`secret=helloworld` → `66987CB115214E59E6EC978214934FB8`。

## 注意

- 排序是 **ASCII 码位序**不是字母序（`foo` < `foo_bar` < `foobar`，因 `_`=0x5F < `b`=0x62）。禁止 locale-aware 排序或 lowercase。
- `sign_method` 三种合法：`md5` / `hmac`（= HMAC-MD5）/ `hmac-sha256`。**md5 与 hmac 的待签串不同** —— md5 前后包 secret，hmac 只用 secret 做 key 不包裹。与抖店相反（抖店 hmac 也包裹），别写混。
- `hmac-sha256` 细节官方正文缺失，仅官方 SDK 有（key=secret，不包裹，64 位大写 hex）。标注为以 SDK 为准。
- **不得写入「淘宝 md5 将下线」** —— 无任何官方来源，官方至今三者并列且自己的完整算例用的就是 md5。
- 网关：默认改 `gw.api.taobao.com`，`eco` 保留兼容。二者关系无官方说明，此为推断。
- 避开混淆源：`developer.alibaba.com` 上的淘宝**全球开放平台**签名串要在前面加 API 名称，套到 TOP `/router/rest` 上必报 `25 Invalid Signature`。

## 通用约束

1. 签名参与集合必须恒等于发送集合减去 `sign`（WP02 提供通用断言，必须启用）。
2. 签名与发送使用同一字符串对象；业务参数 JSON 只序列化一次并缓存。
3. 契约声明文档中每项结论标注官方出处 URL，区分「官方明文」与「推断」。
4. 官方缺失/矛盾项按 spec.md §8 处理，不得推测填充。
5. 交付需附 wire 层断言：参数名集合、传输位置、timestamp 格式。
