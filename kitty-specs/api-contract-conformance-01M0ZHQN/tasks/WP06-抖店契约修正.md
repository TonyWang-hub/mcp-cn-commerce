# Work Package Prompt: WP06 – 抖店契约修正

实现 FR-007。`servers/doudian/server.py` 有自己的 `request()` 与 `_sign()`。

## 官方契约 vs 现状

| 项 | 官方 | 现状 |
|---|---|---|
| `method` | **必填**，点分格式（URL path 去掉开头 `/` 后其余 `/` 换 `.`，如 `/order/detail` → `order.detail`） | **完全没发**（只拼进 URL path） |
| `param_json` | **必填**，业务参数序列化后的 JSON 字符串，置于 **POST body**（`Content-Type: application/json`）；其余字段走 query | 业务参数直接放 POST JSON body，无 `param_json` 参数 |
| 签名串 | `secret + "app_key"+ak + "method"+m + "param_json"+pj + "timestamp"+ts + "v"+v + secret` | `md5(app_key + param_json + app_secret)` —— 缺 method/timestamp/v，拼接顺序也不同 |
| 摘要 | `hash_hmac("sha256", signPattern, app_secret)` —— **消息体仍前后包裹 secret**，同时 secret 又作 HMAC key | md5 |
| `sign_method` | 选填但**不传则服务端按 md5 验签** → 用 hmac-sha256 必须显式传 `sign_method=hmac-sha256` | 传了 `md5` |
| timestamp | Unix 秒（官方注解裁决：datetime 格式"支持但不推荐"） | **Unix 秒 ✅ 正确** |
| `v` | `2` | ✅ |
| `access_token` | ✅ | ✅ |
| **错误信封** | **待核** —— 官方现行判错字段需在契约声明中给出结论 | 现状按 `code != 10000`（`servers/doudian/server.py:183-192`） |

## 错误信封必须给出结论（不得留给实现时现场裁决）

现状按 `code != 10000` 判错。抖店官方现行的响应信封与错误字段名（是否为 `err_no` / `message` / `sub_code` 等）**在前期调研中未核实**。本 WP 必须在 `docs/api-contracts/doudian.md` 里给出明确结论 —— 无论结论是「现状正确」还是「需改」，并标注官方出处。

理由：若官方信封与现状不符，错误会被当成业务数据返回给模型 —— 这正是 plan IC-06 判定为「最危险一类」的缺陷。

## param_json 构造（官方三条硬要求）

1. **保证 JSON 所有层级上 key 有序**（递归排序）
2. **数值不带多余小数点**：`1.0` → `1`。Python `json.dumps` 会输出 `1.0` → 签名必错，需自定义序列化
3. **禁用 HTML escape**：`&`、`<`、`>`、`/`、中日韩、Emoji **都不转义**

另需 compact 无空格、单行。

## 注意

- **`sign_v2` 不要发** —— 那是 SPI（平台反向调用你）方向的参数。SPI 验签规则与 API 方向不同（不含 method 和 v、用 MD5、转义要求相反），本 WP 不涉及。
- md5 公式官方**未给 API 方向的代码**（只给了 hmac-sha256）。按 spec.md §8：**只实现 hmac-sha256，不实现 md5**。
- 官方在线签名工具 `op.jinritemai.com/docs/guide-docs/gen-sign`（公开）用于验收比对。
- 官方要求用 POST；GET 方式"后续可能弃用"，且 `param_json` 含 `#` 会导致 HTTP 414。

## 通用约束

1. 签名参与集合必须恒等于发送集合减去 `sign`（WP02 提供通用断言，必须启用）。
2. 签名与发送使用同一字符串对象；业务参数 JSON 只序列化一次并缓存。
3. 契约声明文档中每项结论标注官方出处 URL，区分「官方明文」与「推断」。
4. 官方缺失/矛盾项按 spec.md §8 处理，不得推测填充。
5. 交付需附 wire 层断言：参数名集合、传输位置、timestamp 格式。
