# Work Package Prompt: WP07 – 小红书重写

实现 FR-008，覆盖 IC-07。**现有实现与官方契约无一处吻合，等于重写该 server。**

## endpoint 修正（审计新增，与契约重写一并进行）

小红书完整 method 面是 **106 个 / 11 个分组**。我们 13 个工具里 **9 个有对应能力，4 个平台根本不提供**。

**需删除的 4 个工具**（改名救不了）：评价列表（106 个 method 全量 grep `review|comment|rate|evaluat` 零命中，小红书商品评价不在电商开放平台范围）、营销活动列表（无 promotion/marketing/activity 域）、优惠券列表（`order.couponList` 是**虚拟卡券商品的履约券码查询**，需带 orderId，返回卡号/卡密，语义完全不同）、店铺信息（无任何店铺名称/类目/评分接口）。

**9 个的官方 method 映射**：

| 我们的虚构 path | 官方 method | 备注 |
|---|---|---|
| `/api/order/list` | `order.getOrderList` | 必填 `startTime`/`endTime`/`timeType` |
| `/api/order/detail` | `order.getOrderDetail` | |
| `/api/product/list` | `product.getDetailSkuList`（SKU 粒度）或 `product.searchItemList`（ITEM 粒度） | 需先定粒度 |
| `/api/product/detail` | `product.getItemInfo` | |
| `/api/refund/list` | `afterSale.listAfterSaleInfos` | **退款不是独立域**，是售后的 `returnTypes` 4/5 |
| `/api/refund/detail` | `afterSale.getAfterSaleInfo` | |
| `/api/inventory/query` | `inventory.getSkuStockV2`（首选） | |
| `/api/logistics/tracking` | `order.getOrderTracking` | |
| `/api/bill/list` | **拆成 4 个**：`finance.pageQueryTransaction` / `finance.querySellerAccountRecords` / `finance.pageQueryExpense` / `bill.downloadStatement` | 账单不是一个列表 |

### 三个实现要点

1. **网关版本混排**：`afterSale.*` 与 `finance.*` 走 `gatewayId=165/gatewayVersionId=2804`，`order.*`/`product.*` 走 `103/1661`，且 165/2804 的接口有 `requestHeader` 入参、信封风格不同 —— **不能用一套请求构造器无脑套**。查文档时必须用各 method 自己的 gatewayId/VersionId。
2. **时间窗约束**：`order.getOrderList` `timeType=1`（创建时间）≤24h、`timeType=2`（更新时间）≤30min 且需**从 `maxPageNo` 倒着翻**否则增量同步会漏单；`pageNo` ≤100、`pageSize` ≤100 ⇒ 单窗口上限 10000 单。
3. **入出参时间单位不一致**：系统参数与业务入参 `startTime`/`endTime` 是**秒**，而出参 `createdTime`/`paidTime` 等是**毫秒**。
4. 官方系统参数文档里 `method` 的 example 至今仍是 **2023-04-13 已下线**的 `package.getPackageList` —— 抄示例必错。

## 官方契约 vs 现状

| 项 | 官方 | 现状 |
|---|---|---|
| 网关 | **单一网关** `https://ark.xiaohongshu.com/ark/open_api/v3/common_controller`，**只有 POST** | `https://open.xiaohongshu.com` + 虚构的 REST path（`/api/order/list` 等，任何版本文档/镜像/SDK 中均不存在） |
| 传输 | 系统参数与业务参数**全部扁平放 POST body**，`Content-Type: application/json;charset=utf-8` | query string |
| 参数名 | `appId` / `method` / `version`(`2.0`) / `timestamp` / `sign` / `accessToken`（小驼峰） | `client_id` / `sign_method` / `access_token` |
| `method` / `version` | 均**必填** | 都没发 |
| timestamp | **秒**（字符串类型） | 毫秒 |
| 签名 | 待签串 = `{method}?appId={appId}&timestamp={timestamp}&version={version}` + `{appSecret}` → MD5 → **32 位小写**。**业务参数与 accessToken 都不参与** | 所有参数（含业务）走 `secret+sorted_kv+secret` → 大写 |
| 判错 | `error_code == 0 && success == true`；业务数据在 `data`，需解包一层 | 查 `error_response`（那是淘宝/拼多多的信封）→ **失败完全检测不到** |

## method 名（官方机器可读接口取得）

订单域：`order.getOrderList`、`order.getOrderDetail`、`order.getOrderReceiverInfo`、`order.getOrderTracking`；售后 `afterSale.listAfterSaleApi` / `afterSale.getAfterSaleDetail`；商品 `product.searchItemList` / `product.getItemInfo`；库存 `inventory.getSkuStock`；财务 `finance.querySellerAccountRecords` 等。完整清单可从 `open.xiaohongshu.com/api/doc/second/listNew?apiNavigationId={14..21}` 取。

⚠️ 官方签名示例里的 `product.createItem` 和 `package.getPackageList` 都是**已下线的老 method 名**（示例未更新）；`package.*` 整个域已被 `order.*` 取代。

## 注意

- 官方文档的 `"path":"/ark/order.getOrderList"` 字段是**文档系统内部注册路径，不是真实调用地址**。真实地址永远是 `common_controller`。
- 系统参数 timestamp 是**秒**，但业务参数里的时间字段（`createdTime`/`paidTime` 等）是**毫秒**。别混。
- 官方文档正文里签名串显示成 `method?appId=xxx& timestamp=...`，`&` 后有空格 —— 官方已注明「拼接字段空格为格式，实际中不存在」。
- `order.getOrderList` 时间窗约束：`timeType=1` ≤ 24h，`timeType=2` ≤ 30min；官方建议单商家轮询 ≥ 5 分钟。
- 第三方 apifox 镜像**已过期**（订单参数仍是 `packageType`/`packageStatus`，现行是 `orderType`/`orderStatus`），不要作为依据。
- 另有一套**消息推送 webhook 验签**规则完全不同（kebab-case `app-key`、待签串含 URL path），本 WP 不涉及。

## 通用约束

1. 签名参与集合必须恒等于发送集合减去 `sign`（WP02 提供通用断言，必须启用）。
2. 签名与发送使用同一字符串对象；业务参数 JSON 只序列化一次并缓存。
3. 契约声明文档中每项结论标注官方出处 URL，区分「官方明文」与「推断」。
4. 官方缺失/矛盾项按 spec.md §8 处理，不得推测填充。
5. 交付需附 wire 层断言：参数名集合、传输位置、timestamp 格式。
